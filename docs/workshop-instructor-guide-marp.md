# 1. 画面操作基礎

---

## チャット・モデル・モード

### チャットウィンドウ
- サイドバー: `Ctrl+Alt+I`（Mac: `Ctrl+Cmd+I`） / インライン: `Ctrl+I`（Mac: `Cmd+I`）

### モデル選択
- 迷ったらバランス型モデルから

### 3 つのモード

| モード | 動作 | 使い所 |
|--------|------|--------|
| **Agent**（デフォルト） | ファイル編集＋ターミナル実行 | 実装・修正・自動化 |
| **Ask** | 質問に回答するだけ | 調査・学習・質問 |
| **Plan** | 計画を立ててから実装 | 大きな変更・設計 |

<!-- デモ: 同じ質問を Ask と Agent で投げて違いを見せる -->


Plan モード：
"◯◯ 社について調べてください" といった、このままだと何を調べたらよいか、AI が文脈を理解できず、回答が不十分になることがあります。そういった場合に、Plan モードで「調査の目的」「調査対象」「調査方法」などを確認してから実行すると、より期待に近い回答が得られます。

# 2. コンテキストの与え方

---

## コンテキスト = 回答品質

| 操作 | 効果 |
|------|------|
| `#file:ファイル名` | 特定ファイルを参照させる |
| `#folder:フォルダ名` | フォルダ配下を参照させる |
| `@workspace` | ワークスペース全体を検索対象に |
| ドラッグ＆ドロップ | 画像・ファイルを直接添付 |
| URL を貼る | Web ページの内容を参照 |

> 多すぎず、少なすぎず — 関連ファイルだけをピンポイントで

# 4. Skill / Agent の仕組み

---

## Skill と Agent の違い

| | Skill | Agent |
|--|-------|-------|
| 役割 | ドメイン知識の提供 | ペルソナ＋ワークフロー |
| 起動 | `description` で自動マッチ | `@agent名` で明示呼び出し |
| ツール | 制限なし | `tools:` で制限可能 |

### 本日使う 4 エージェント（`.github/agents/`）

- `sdd-1-requirements` — ヒアリング → 要件一覧
- `sdd-2-design` — 要件一覧 → 設計書
- `sdd-3-wireframe` — 設計書 → ワイヤーフレーム（`app/index.html`）
- `sdd-4-pipeline` — `app/` → Azure Static Web Apps への CI/CD

---

## エージェントの呼び出し方（2 通り）

### ① チャット入力欄で `@エージェント名` と入力する（本日はこちら中心）

```
@sdd-1-requirements #file:samples/meeting-notes-sample.md をもとに要件一覧を作成してください。
```

### ② モード選択ドロップダウンから選ぶ

1. チャット入力欄下部の「Agent」等と表示されたモード選択ドロップダウンをクリック。
2. 一覧から `sdd-1-requirements` などのエージェント名を選択（以降のメッセージはそのエージェントとして実行される）。
3. 通常どおりプロンプトを入力して送信。

# 5. 簡略化 SDD ライフサイクル

---

## なぜ簡略化するか

- 会議議事録などの雑多な情報から、いきなり実装に入ると前提・要件の考慮が抜けがち。
- フル機能の GitHub Spec Kit（constitution → specify → clarify → plan → analyze → tasks → checklist → implement）は複数の確認ゲートがあり、短時間のワークショップには重い。
- 本ワークショップでは以下のステップに簡略化する。

```
ヒアリング（議事録） → 要件定義書 → 設計書 → ワイヤーフレーム → デプロイ
```

- 各フェーズを専属エージェントに担当させ、役割・出力形式を固定する。

# 10. 応用トピック（駆け足）

---

## MCP / Coding Agent / 品質管理

- **MCP サーバー連携**: 外部データソース（Azure・Dataverse 等）を Copilot から直接利用。
- **Coding Agent**: GitHub Issue に Copilot をアサイン → 自動で PR 作成。
- **品質・信頼性**: 重要な事実は必ずソースを確認。生成結果は必ず検証する。
